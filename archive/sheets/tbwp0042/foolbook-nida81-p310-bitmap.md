# nida81 P310 "IBM PC Compatible Computer": why the bitmap is missing in Foolbook r15
Written 2026-10-25 (Asia/Tokyo). Revision tested: Foolbook **r15 = 63e92fd (tag v1.0.7r15, newest)**, real viewer under Xvfb, Python 3.13.5 / Tk 8.6.16 (Liberation Sans), page at scale 1.0. Read-only on every repo; scratch in /workspace/repro.

## Result in one paragraph
Reproduced. Clicking the P300 bar "1. IBM PC Compatible Computer" does open nida81 at P310 and draws the heading bar, the "Minimum Requirements" list and the two arrow buttons, but **the computer picture is a plain white rectangle** (371 x 397 px at page position 72,63), which also hides the left half of the white bullet text. Two separate defects, both in how nida81 is stored/read:
1. **Object class 0x19 (picture) is not decoded.** nida81.tbk has 39 objects of class 0x19, spread over 26 pages (P310, P320, P330, P335, P350, P355, P356, P357, P360, P370, P375, P376, P380, P390, P395, P20000, P20001, P22045, P22050, P22060, P22070, P22080, P22100, P22110, P22120, P22130). 9e954d01.TBK has none (its pictures are class 0x15 or button bitmaps, which the reader does decode). In openscript_analysis `formats/tbk/store.py` the class table `_CLASSES` has no 0x19 entry, so the object falls back to a plain rectangle ("rect", fill #fff, outline #000, align 254) in `_store_shape`, and `engine/loader.py::_png` only makes an image when the bitmap bytes begin with "BM", which never happens for this class. So no code path ever reaches the picture data.
2. **core/nida81.fsk is a text-only stub.** It has 43 pages, the page text (P310: "Minimum Requirements 586 133 MHz ...") and 29 cross-book links ("P20001@nida81.tbk"), but no drawn items. If nida81.tbk is not found beside the book (or in a parent or child folder; `find_book` tries here, parent, child dirs, then core/, each with .fsk .sbk .fbk .tbk .json) the P300 bar lands on an empty white page; I tested this in an isolated folder (image `foolbook-r15-P300-click-stub-only.png`, fully white). So a user without nida81.tbk next to the lesson sees "does not render" even before the picture problem.

## What the file holds (class 0x19, P310)
- Raw 89-byte 0x19 record of the P310 picture: width at +0x41 = 371, height at +0x43 = 397, depth at +0x45 = 8, a dword at +0x2D = 141758 (the stored data size) and a dword at +0x29 = 0x48ae0, +0x51 = 0xf8.
- The pixel data is in the bitmap table at header+0x104 (rows: size, unused, offset). Two rows have size 141758 (file offsets 0x1c58f2 and 0x3d5cc5; probably the computer picture used on P310 and on P20001, not checked). The data begins `af 16 fe 01 00 09 00 00 03 60 45 02 00 00 f8 94 22 01 00`.
- I tried two decodes and both failed: plain BI_RLE8 (the stream ends after 9 end-of-line markers, far fewer than 397 rows) and a BMP wrapper with the segment palette (the palette is all white and the data runs short: "not enough image data"). The 0x19 payload is a different compressed form (TB80CMP.DLL is the candidate for the compressor; not confirmed). **I did not decode it**, so I cannot say which compression it is; this is where the next work is.

## Where to fix (read-only, no edits made)
1. openscript_analysis `formats/tbk/store.py`: add class 0x19 to the object classes and a decoder for its data (table at header+0x104, size field at record +0x2D, width/height/depth at +0x41/+0x43/+0x45), producing a bitmap/PNG, as `_paint_bmp` does for class 0x15. Until the compression is decoded, a transparent placeholder is better than a white rectangle, which hides text (a white fill that is not in the file).
2. Foolbook `engine/loader.py::_png` and `_store_shape`: use the new bitmap; otherwise do not draw a filled white rect for an unknown class.
3. core/nida81.fsk: the stub only stores text and links. Either ship a full nida81.fsk (with decoded pictures) or make the viewer say that nida81.tbk is needed instead of showing a blank page.

# Foolbook: why the user's viewer draws the type too big (and what r14/r15 do about it)
Written 2026-10-25 (Asia/Tokyo). Read-only on every repo. All work in /workspace/repro (venvs, scripts, outputs). Nothing written into a repository, nothing touched in opentoolbook8, Graal or Seihai.

## 1. Short answer
- **Reproduced.** The user's four screenshots (P400 of 9e954d01) are matched wrap for wrap ("INTRODUCTI/ON", "Inp/ut", "Out/put", "Digit/al/Circu/it", "74LS174N / E825", body breaking before "thought") when the **r12 code's type size is sent to Tk as a point size at a Tk scaling of about 1.45** (about 104 dpi). Image: `/workspace/reports/foolbook-user-oversize-vs-repro.png` (user's post12 shot left, my reproduction right).
- r12 computes a pixel size (12 pt x window scale x 96/72) and means it as pixels (negative Tk size). On the user's machine Tk draws it about 1.45x larger than that. I could **not** make any Tk I have do this on its own (see 3), so the exact Tk/desktop switch on the user's side is **not proven**. What is proven: the numbers in the user's pictures fit "pixel size drawn as points at ~1.45 scaling" and nothing else I tried.
- **Which revision the screenshots show:** s3 and s4 match r12 (post12) sizing exactly. Screenshots 1 and 2 label post13 in the terminal behind the window, but the open window's type fits r12, not r13 (r13 asks for a smaller size than r12), so I believe that window was a stale post12 process. This is an inference, not proven.
- **Revision map:** `1.0.7.postN` is tag `v1.0.7rN`. post12 = 313e4eb (window opens at page size), post13 = cf1031c (drops the 96/72 factor: type 25 % smaller than r12 on every Tk that honours pixels), r14 = 1115f88 (puts 96/72 back), **r15 = 63e92fd (newest, tag v1.0.7r15)**: sizes the type from the face Tk really draws.

## 2. Evidence
Window scale from the blue page area of each user screenshot (624 px page width): s1 0.625, s2 1.006, s3 1.064, s4 1.69 (measured on the files). r12 asks Tk for round(12 pt x scale x 96/72) px for the P400 body, i.e. 17 px in s3.
- s3, P400 body line 1 "Digital circuits and the IC chip are usually": **about 488 px wide in the user's shot**. A 17 px Liberation Sans Bold line of that text is 337 px wide (PIL measure), so the user's type is **1.45x bigger than r12 asked**.
- My reproduction (r12 code, size sent to Tk as a point size, tk scaling 1.45, window opened at the user's s3 geometry, scale 1.0656 against the user's 1.064): the same line is **about 493 px** and every wrap the user shows appears: INTRODUCTI/ON, Inp/ut, Out/put, Digit/al/Circu/it, "74LS174N / E825", and the body breaking in the same place. Compare image `/workspace/reports/foolbook-user-oversize-vs-repro.png`.
- That is exactly what Tk does with a point size: pixels = points x `tk scaling` (1.45 is about 104 dpi, like a 27-inch 1440p screen at 109 dpi, or a Xft.dpi of about 104 to 109).
- I did not re-measure s1, s2 and s4 glyph widths with the same care; their page scales are above. The s1/s2 terminals say post13 was being installed, but I believe the open window was still the previous post12 process (my earlier look at the glyph size against what r13 asks); treat this as a caveat, not a proven fact.

## 3. What I tested that did NOT reproduce it (negative sizes stay pixels)
Revisions r12, r13 and r15 installed from git archives (same tree as the tags) into new venvs under /workspace/repro (`venv314_r12`, `venv314` = r13, `venv314_r15`), openscript-analysis 1.0.1.post4 (= tag v1.0.1r4, as pinned). The "0.0.2)" in screenshot 1 is the tail of `cryptography 50.0.2`, not openscript-analysis.
- Python 3.14.9 (uv build) with **Tk 9.0.4**, Xvfb; this Tk has **no Xft** (only X core families such as "nimbus sans l"; no Liberation or Arial), tk scaling 1.0 to 3.0: negative sizes stay pixels.
- System Python 3.13.5, **Tk 8.6.16** with Xft (Arial maps to Arimo/Liberation Sans), with and without an Xft.dpi change: negative sizes stay pixels.
- A Debian **Tk 9.0.1 with Xft** (`wish9.0`, in /workspace/repro/tk9deb) at Xft.dpi 96 to 192 and tk scaling 1 to 3: negative sizes stay pixels. A positive size is the one that follows the dpi.
- cpython gh-143990 (Python 3.14.x `tkinter.font.Font(font=(name,-N,..))` resolves the pixel size to a rounded point size for measuring): affects `measure`, not drawing.
So no Tk I had turns -N into points. The user's Tk/desktop does (or enlarges the face by 1.45 some other way). Candidates, ranked: (1) a Tk/Ubuntu build or HiDPI/fractional-scaling setup where pixel-sized Xft faces are scaled by dpi (Tk ticket 1de3a48312 describes pixel Xft fonts changing with `tk scaling`, fixed in Tk 9.1b1; Tk 9.0 sets `tk scaling` from Xft.dpi); (2) a font substitute for "Arial" much larger than Liberation; (3) something else on that machine. **Cheapest proof:** ask the user for `python3 -c "import tkinter as t,tkinter.font as f;r=t.Tk();F=f.Font(font=('Arial',-16,'bold'));print(r.tk.call('info','patchlevel'),r.tk.call('tk','scaling'),F.measure('INTRODUCTION'),F.actual())"` and `fc-match Arial`. A normal desktop prints about 123 for the measure; about 178 would confirm the point-size theory.

## 4. The code that produces the size
- `engine/place.py` `place_window` (r12 `engine/place.py` lines 175-176): `item["size"] = max(1, int(round(recorded * scale * 96 / 72)))` and `item["px"] = True`. Every text field and run goes through here; this is the single place the window scale reaches type.
- `engine/graphics.py` `_typeface` (r12 `engine/graphics.py` line 432): `size = -abs(int(size))` when `px` is set, then `create_text(font=(face, -N, style))`. A negative number is the pixel size on every Tk I could test. On the user's machine this is the line that does not behave.
- Positive (point) sizes behave as the user sees: Tk converts points with `tk scaling` (pixels = points x scaling), so a point-sized font also changes with the desktop dpi, which is one reason pixel sizes were used.

## 5. What the newest revision (r15, 63e92fd) changed
- `_family()` picks Liberation Sans, Nimbus Sans, FreeSans, Arial or DejaVu Sans if present.
- `_ink_factor()` measures "INTRODUCTION" in that face at -16 px bold once and divides it by 123 px (Liberation Bold at 16 px). `_typeface` divides every pixel size by that factor, so a desktop that draws 1.45x wide gets the size divided back. Fonts are now cached named `tkfont.Font` objects, not tuples.
- `_fit_words()` / `_fit_text`: a label whose longest word is wider than its box drops a pixel at a time until the word fits.
- **Test result of r15 (real viewer, Xvfb):**
  - Emulating the user's Tk (a shim in my wrapper turning negative Font sizes into points, tk scaling 1.45, same Tk 8.6 / Liberation): at 683x540 and at 1896x1000, "INTRODUCTION" one line, "Digital Circuit" two lines, "Input" one line, body breaks after "one and" exactly like ToolBook. **INTRODUCTI/ON, Digit/al/Circu/it and Inp/ut are gone.**
  - **"Output" is still split ("Outpu" / "t") at 683x540 and at 1896x1000** on Tk 8.6 / Liberation, with or without the emulation (image `/workspace/reports/foolbook-r15-P400-683x540.png`). Cause: `_fit_text` shrinks the size (my check: `_fit_words` returns 10, `_fit_text` returns 10) but `_typeface(shape, size)` then does `if recorded: size = recorded` with the shape's own 13 px and the shrunken size is thrown away; the draw still uses -13. The fix belongs in `_typeface`: take the size argument when the caller has already fitted it (r15 `engine/graphics.py` lines 471-479: `recorded = int(shape.get("size") or 0)` then `if recorded: size = recorded`, before the ink-factor division at 479; `_fit_text` is at 526).
  - Tk 9.0.4 (no Xft, Nimbus Sans): "Output" fits at 1896x1000; P400 otherwise fine.
  - P1040 (coloured letters): at 683x540 and at 1896x1000 the yellow letters print on top of their neighbours ("TransistorLogic (TTL)" overprint) and "family of" ends line 1. ToolBook breaks after "family". At 1:1 the break is one word early the other way ("family" starts line 2). So P1040 matches ToolBook at none of the three sizes. Image `page-compare-r15/r15_P1040_sizes.png`.
  - P2170: normal run fine (header on one line). In the user-Tk emulation at 683x540 the header "POWER (mw)" breaks to a second line. Image `page-compare-r15/r15_P2170_sizes.png`.
  - P450: fine at all three (image `page-compare-r15/r15_P450_sizes.png`).
- Recommended fix location (do not edit): `engine/graphics.py` `_typeface` for the lost fitted size, and a decision whether to keep the probe (it fixes the user's machine) or send point sizes through `tk scaling` explicitly. The probe is a good instinct: it makes the type follow what the desktop really draws.
